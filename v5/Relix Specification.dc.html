1. Introduction

1.1 Purpose

This document is the main functional and technical reference for Relix. It describes business rules, entities and data model, statuses and workflows, permissions, default configuration and the consistency rules between modules. It extends the v1 specification (“CMMS MVP”) and keeps its concepts, terminology and structure wherever the current Relix design does not change them. When the current design conflicts with v1, the Relix behavior described here prevails.

1.3 Conventions used in this document

  • Required fields are marked “Yes” in the tables and with a red asterisk in forms. A form cannot be saved (or a wizard step cannot be left with “Next step”) while a required field is empty or invalid.
  • Field types: uuid, string(n), text, int, decimal(p,s), bool, date, datetime (UTC, displayed in the site time zone), enum(…), json, fk → table.
  • Table names are singular snake_case; every table has id (uuid, PK), created_at, created_by, updated_at, updated_by unless stated otherwise (not repeated in each table).
  • Site-scoped tables carry site_id fk → site (required). Organization-level tables (businesses, sites, users, super-user scopes) are not site-scoped.
  • Reference data is never hard-deleted while in use: it is deactivated (active=false) and kept for history. Deletion is refused with a usage message when referenced.
  • Human-readable identifiers (WO-…, R-…, asset codes, part references) are unique per site and immutable once created, except where stated.
  • “Site configuration” is the in-app name of v1 “Administration”. “Work order” (WO) is the v1 “Ordre de travail / Intervention”. “Intervention” in Relix designates the execution of a work order.

3.3 Cross-cutting behaviors (updates v1 §2.3 and §19)

  • Every page fits the screen height: header and toolbars stay fixed; only content regions scroll. Lists scroll internally with sticky column headers and a pagination footer (page size selectable).
  • Lists provide search, filters, per-row actions (“…” menu) and pagination. Row click opens the object; explicit buttons perform actions (e.g. Start intervention).
  • Creation and edition open in a right-side panel or wizard without leaving the context.
  • Status indicators always combine a label with a visual cue; color is never the only carrier of information.
  • Destructive actions require a confirmation. Deleting referenced data is refused with an explanation (usage check); deactivation is proposed instead.
  • Dates must be consistent (e.g. desired date ≥ request date, request date not in the future); invalid input is blocked.
  • Statuses, priorities, types and categories come from controlled reference lists (system or site configuration).
  • Every object change that matters is historised (work order history, asset history, maturity log).
  • Every page has a Back button returning to the previous page (fallback: Home).
  • Deep links: work order (with optional chat and message), chat conversation, intervention request, asset detail tab, Site configuration section, Teams & users tab.

4. Organization, sites and site context

4.1 Organization hierarchy

  • One organization (tenant) contains businesses (level 1), optional sub-businesses (level 2, parent = a business) and sites attached to a business or to a sub-business. Deeper levels are not allowed.
  • The organization structure is managed only in the Super Admin area. Site configuration does not contain any organization or site management.
  • A business or sub-business cannot be deleted while it contains sub-businesses or sites. A business with sub-businesses cannot become a sub-business.
  • A site cannot be deleted when it holds data (assets, work orders, stock); it is set inactive instead. Inactive sites disappear from all site switchers but keep their history. The site currently open cannot be deleted.
  • Names are unique among businesses/sub-businesses; site codes (3–4 letters, uppercase) are unique in the organization and immutable.

4.2 Site creation (Super Admin)

New site is a 3-step flow; each step must be valid before “Next step”.

  1. Identity — Site name*, Code* (3–4 letters, unique), Business*, Sub-business (optional, filtered by business).
  2. Location — Country*, City, Latitude* (−90…90, decimal degrees WGS 84), Longitude* (−180…180), Time zone (proposed from the country).
  3. Site administrators — at least one administrator is required so the site is manageable from day one: existing users (searched across the organization) and/or invitations (full name + email; email must not already exist).

On “Create site”: the site is created with the default site configuration (§10.2); each chosen user receives the Administrator role on this site (user_site_role) and the site is added to their site access; invited administrators are created with status Invited and receive an invitation email. Administrators can then invite the team, create teams, define the plant hierarchy and adapt the configuration.

4.3 Current site

  • Each user works on one current site at a time (stored per user, restored at sign-in). Switching site reloads site-scoped data; all lists, KPIs, planning and configuration show the current site only.
  • The Site dashboard shows the business path of the site, local time and site KPIs (overdue work orders and critical ones, stopped equipment, preventive compliance, parts out of stock / low, work due today and done).
  • The site’s maturity levels (§7.21) and units (§7.18) are those of the current site.

7.1.4 Identification and display

  • A work order is identified by its title “Asset — Task”; the WO ID is shown as secondary information.
  • Overdue items are highlighted with “N d late”. Urgent = Critical or High priority (marked as urgent); other priorities are shown as normal text.
  • Row click opens the work order; explicit Start / Resume buttons run the intervention.

7.1.5 History

Every change of status, priority, assignee, planned date, waiting flag, type, title or asset is appended to the work order history with author and time; creation, generation from a plan, quick start and completion are recorded as events. History is visible in the work order “History” section.

7.1.6 Follow-up and root cause

From a completed work order, a follow-up work order can be created (link parent_wo_id, notification wo-followup). Corrective work orders can carry a root cause analysis (cause, 5 whys, corrective action).

7.2 Work order creation

Creating a work order from anywhere (Home, Work orders, Asset detail, Planning slot, request, chat) opens the same right-side 4-step wizard. Links to “new work order” are intercepted to open the wizard. Creation is refused for users without Work orders Edit access (they are invited to send an intervention request).

StepFields and rules
1. Essentials*Asset* (prefilled from context), Type*, Task (title)*, Priority*. “Next step” is disabled until mandatory fields are filled.
2. ChecklistsSelect published checklists (optional). Required spare parts/consumables and mobile assets of the selected checklists are added automatically (tag “From checklist”); estimated duration = Σ step minutes.
3. PeopleAssigned users (one per checklist part, suggestions by skill and availability, §7.7) and Include in follow-up. Never “Participants”.

Footer: Cancel / Previous, “Next step” (disabled until the step is valid), “Create work order” on the last step only; option “Create another”. On creation: number generated, status Requested (no date) or Scheduled (date + assignee), history “Created”, event wo-created, notifications to assignees (wo-assigned), work order chat channel created with assigned users and followers. If created from a request, the request becomes Accepted and is linked.

7.3 Quick intervention

  • For an immediate breakdown. Same right-side panel shell as the wizard, 2 steps: Equipment (search or QR scan) → Issue (short description, type). Footer Cancel/Previous + Next step → Start intervention.
  • Creates a work order with quick=true, status In progress, assignee = current user, and opens the intervention immediately. The work order shows “Information incomplete” until Priority, Description and Failure category are completed (required at Review & close).

7.4 Intervention requests

  • Any signed-in user, including Requesters and production operators, can send a request: asset* (search/QR), short description*, optional photo, people and/or teams to notify. A request is not a work order.
  • Lifecycle: Report issue → Notify → Review (Pending → Accepted or Not retained) → Create work order if needed.
  • Notified users and members of notified teams receive a wo-request notification. A request is relevant to a user if they reported it, were notified, or one of their teams was notified.
  • Decision: by a notified user (or any Work orders Full user) with Work orders Edit access. “Not retained” accepts an optional reason shared with the reporter. “Create work order” opens the wizard prefilled (asset, title from the description, description + “From intervention request R-… · reported by …”, type Corrective, followers = decider + reporter); on creation the request becomes Accepted and links the work order.
  • Home shows the block “Intervention requests” with To review / All views; the block is hidden entirely when nothing is pending for the user.

7.5 Intervention (execution)

  • Entry: Work order detail “Start intervention” / “Resume intervention”, Home to-do Start/Resume, quick intervention. Only assigned users (or Work orders Full users) can start or resume. Unassigned viewers get “Ask” (opens the work order chat).
  • Focused mode without the menu: one step at a time, “Step N of M”, Previous/Next, Pause, “Review & close”. The work order chat is permanently docked on the right.
  • Each assigned user executes the checklist parts assigned to them; parts of others are shown read-only with the person in charge.
  • Required steps block “Next” until answered; rules (§7.6) can skip steps, require a photo/comment or finish the checklist.
  • Pause: stores progress (current step, answers, worked time) and sets the waiting flag (paused, or parts when paused for a missing part); a system message is posted in the chat; followers receive int-paused. Progress summary is visible elsewhere (e.g. “3 of 7 steps”).
  • Review & close: summary of answers and flagged anomalies, actual time, parts and consumables used (UsageInput), photos, report; quick interventions must complete missing information. On close: status Completed, completed_at, actual time, usages recorded on the work order, stock deducted once (stock_done), part reservations consumed, actual costs computed, history “Completed”, notification int-completed to followers, asset history updated, meter reading proposed for meter-based assets.
  • Flagged anomalies can create a follow-up work order directly.

7.6.2 Rules and flow

  • Default flow: next step in order. A step can define after = next / goto step / finish.
  • Rules per answer: goto a step, require a photo or comment, finish the checklist. Conditional steps are reached only through a rule; skipped steps are recorded as skipped.
  • flag_when marks an answer as an anomaly (shown at review, can trigger a follow-up).
  • Two editing views share the same model: Checklist view (ordered list, expandable step editor, quick-add) and Workflow view (Start and End fixed, palette of step types, automatic layout, connections drawn between steps, insert zones, side-panel step editor). Each rule is a connection in the workflow view.
  • Consistency checks on publish: every goto target exists, no step unreachable (except conditional steps reached by a rule), at least one path to End, required options defined for choice steps.
  • Preview mode runs the checklist in the intervention screen without creating data.
  • A checklist used by work orders keeps a version snapshot per work order: editing a published checklist does not alter running interventions.

7.6.3 Skills, duration, equipment and parts on steps

  • Each step can carry required skills, estimated minutes, required mobile assets (tools) and, for parts/consumables steps, spare parts with quantities.
  • Consecutive steps with the same skills form a part (steps without skills join the previous part). Conditional steps are excluded. Parts are sequential: offset = Σ previous part durations.
  • Required parts of a work order = aggregation of its checklists’ parts/consumables steps (partsOf), plus manual additions, minus dismissed.

7.7 Skills and assignment (multiple assignees)

  • Skills catalogue per site (Site configuration › Skills): Trade, Technique, Certification. Users hold skills with a level 1 Basic / 2 Qualified / 3 Expert.
  • Assignment is per checklist part: one person per part (the same person can take several parts). The work order assignee is the first assigned user. A work order without checklist has one or more assigned users for the whole duration.
  • Suggestions rank people by: has all required skills (mandatory to be “matching”), available at the planned time (§7.8), sum of skill levels, free hours that day. Auto-assign keeps the same person on consecutive parts when possible.
  • People selection fields everywhere (wizard, work order edit): Assigned users (perform the work; parts derived by skill) and Include in follow-up (not assigned; chat + updates; follower role “Follow-up”). A person cannot be both.
  • Assigning someone without the required skill is allowed only with an explicit warning; assigning someone unavailable shows the reason (off, absent, other site, outside shift).

7.8 User availability

  • Availability for a time window on a date at a site: not working that weekday → unavailable “Not working that day”; shift at another site → “At {site}”; full-day absence (or part-day absence overlapping the window) → absence label; window outside shift hours → “Works hh:mm–hh:mm”; otherwise available.
  • Capacity of a day = shift hours minus part-day absence; free hours = capacity minus planned work.
  • Current status on profiles: absent, off today, at another site, on shift until hh:mm, or shift hours.
  • Users edit their own profile (skills require manager validation if configured); managers and administrators edit profiles of their site users.

7.9 Planning and scheduling

  • Views Day / Week / Month (v1 §11), navigation previous/next/today, filters (technician, team, type, priority). Planning day 0 is Monday; weekends are non-working by default.
  • Backlog: open work orders without planned date (Requested), with their parts per skill (segs [{skills, hours, who}]). Dropping a backlog item on a slot splits it into one event per part/person.
  • Slots where nobody qualified and available exists are striped and refuse drops; Day view shades off-shift and absence hours.
  • Slots where a required mobile asset is already reserved are striped (equipment) and refuse drops; drops on reservations created by other work orders are refused with the next free slot proposed.
  • Scheduling sets planned_start, status Scheduled, creates mobile asset reservations for the event duration, and notifies the assignees (plan-change on move/reassign).
  • Home “Not scheduled” cards open a slot dialog (Today / Tomorrow / Thursday / Friday, “All day” or free slots of the assignee computed from shift, absences and already planned work).
  • Preventive work orders generated by plans are loaded in Planning with their due date.
  • Workload KPIs: scheduled, overdue, critical, planned hours, average load rate (planned hours / capacity).

7.10 Mobile assets and reservations

  • Mobile assets (cranes, lifts, forklifts, measuring instruments, tool kits) are assets of class mobile; they have a home location and can be reserved.
  • Checklist steps reference required mobile assets; work orders store wo_tool (automatic from checklists, editable).
  • Reservation conflicts: two reservations of the same mobile asset cannot overlap. Work order creation and edition are blocked while a required mobile asset is reserved at the chosen time; the next free slot is proposed.
  • Asset detail of a mobile asset has a Reservations tab (in use now / upcoming / past). Internal equipment time is costed at the internal hourly rate of the asset type or asset (§7.13).

7.11 Spare parts and consumables

  • The Spare parts module is the single source of truth for items: kind Replacement part (whole units) or Consumable.
  • Consumable usage modes: amount (in stock unit or a sub-unit mL/g/cm converted to L/kg/m) or percent (percentage of one unit: stock becomes fractional, shown as “3 rolls + 1 opened (65%)”).
  • One adaptive input (UsageInput) is used everywhere a quantity is entered: stepper (parts), amount field with unit (amount), slider (percent) — in step editor, work order panel and intervention.
  • Required parts on a work order create reservations; available stock = qty − reserved. A required part out of stock notifies the assignees (part-unavailable) and can set the waiting flag parts.
  • Stock decreases only through stock movements: consumption at intervention completion (once), manual adjustment (with reason), receipt, transfer between storage areas, return.
  • Low stock (qty < min) notifies stock followers (part-low); KPIs: references, stock value (Financial), low stock, out of stock.
  • Each part is stored in a storage area (a plant Step flagged storage) + bin; links to equipment (where used), preferred supplier and supplier reference, cost center, GTIN (validated), item code, image, custom fields.
  • Export (CSV) of the filtered list; the Unit cost column is empty without the Financial permission.
  • Deletion of a part referenced by checklists or open work orders is refused; it can be deactivated.

7.12 Plant hierarchy and assets

  • Hierarchy Plant › Zone › Line › Step, edited in Site configuration › Plant hierarchy (add zone/line/step, rename, delete when empty). Storage areas = Steps with storage.
  • Assets are attached to a Step. Sub-assemblies and components (v1 levels 4–5) are modeled as child assets (parent_asset_id).
  • Assets page views: List (zone cards + filters; flat list or “By location” accordion Zone › Line › Step › assets), Hierarchy (searchable tree + node chart with zoom and selected-node card) and Plant layout (map, to be fitted later on the real plant drawing). The chosen view is remembered.

7.20 Autonomous vs standard maintenance

  • Standard maintenance (maintenance_mode = standard): performed by maintenance staff (Technician, Planner, Manager roles) with the full work order lifecycle.
  • Autonomous maintenance (TPM, v1 strategy “Autonome”): simple routine tasks (cleaning, inspection, lubrication, tightening) performed by production operators. Rules:
    • Defined by maintenance plans or work orders flagged autonomous, with short checklists (inputs, checkbox, photo; no spare parts beyond consumables).
    • Assigned to operators (typically Requester role) or a production team; the assignment does not require maintenance skills.
    • Executed in the same intervention mode; anomalies flagged during execution create an intervention request for maintenance automatically (not a work order).
    • Not shown in the maintenance workload of Planning unless an assignee belongs to maintenance; reported separately in KPIs (autonomous compliance).
  • Requesters need Work orders View plus the capability “Execute autonomous tasks” granted by their assignment; they cannot create standard work orders.
Autonomous maintenance is specified here as the target rule; the current prototype does not yet expose the maintenance_mode switch (see §11).

7.21 Maturity levels

  • Each site chooses, for 10 concepts (Work orders, Checklists, Planning, Preventive maintenance, Assets, Spare parts, Maintenance organization, Documents, Notifications, Performance), a level 1 Essential ★, 2 Advanced ★★ or 3 Expert ★★★, each with a short non-technical description and “what you can do”.
  • Global score = Σ levels / (10 × 3) (e.g. 18 / 30 ★) with a journey stage: Getting started (< 50 %), Building up (≥ 50 %), Well established (≥ 70 %), Expert site (≥ 90 %). Level 1 is a valid way of running maintenance, not a deficiency.
  • Changes are logged (concept, from, to, by, at). New sites start at level 1 everywhere.
  • Custom mode: on top of the levels, each catalogued feature can be switched on or off individually (override). Picking a level for a concept resets that concept's overrides. Features may require another feature (e.g. mobile equipment per step requires mobile equipment) and AI features also require the Advanced features switch.

7.21.1 Principles

  • Levels change complexity, never the availability of fundamentals. At level 1 a site can report an issue, create an intervention, attach and run a simple checklist, assign someone and close the work.
  • Gating hides interface, never data. Switching a level down never deletes anything. A field that already holds a value stays visible and editable; an existing checklist runs completely in Intervention, whatever its step types (authoring is gated, execution is not).
  • Progressive disclosure. Optional fields are not displayed by default; they are offered as small “+ Label” chips that add one field at a time. Only chips for features that are on are offered.
  • Consistency. A feature switched on is usable everywhere it applies (creation wizard, intervention detail and edit, Planning, Intervention); a feature switched off disappears everywhere, including its Site configuration section.
  • No artificial third level: where nothing meaningful differs between two levels, the feature is available from the lower one.

7.24 Maintenance plans (preventive)

  • Trigger time (calendar): next due = last done + every × unit (days, weeks, months, years). Trigger meter: next threshold = last meter value + every; the due date is estimated from the asset’s average daily meter rate; “due now” when the current reading reaches the threshold.
  • Lead time: a plan generates its work orders lead_days before the due date. Generation runs at least once a day (on every page load in the prototype) for active plans.
  • Generation creates one preventive work order per asset of the plan: task = plan name, type = plan type, status Scheduled, planned start = due date 08:00, checklist = plan checklist, estimated duration, default assignee, description “Generated from maintenance plan …”, plan_id, created by system, history “Generated from maintenance plan”. A plan-due notification is sent. The plan reference (last done / last meter) advances.
  • Manual “Generate now” creates the work orders for the next occurrence (due tomorrow if not yet due) and records the generation as manual.
  • Deactivating a plan stops generation; already generated work orders remain. A plan with a checklist that is archived cannot be activated.
  • Inspection and calibration plans feed the Home Reminders (controls & calibrations due within 60 days; overdue shown first) and the “Control / calibration due” alert rule.
  • Plan list: name, assets, frequency, checklist, estimated duration, next due, status; detail shows generation history.

7.25 Meters

  • Assets with a meter unit record readings (manual from Asset detail › Preventive, at intervention close, or live feed). A reading lower than the previous one is refused (meter reset must be recorded as such).
  • The daily rate (average over recent readings) estimates meter plan due dates.
